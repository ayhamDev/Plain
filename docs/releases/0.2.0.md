# P.UI 0.2.0

**Status:** Integrated local candidate; subsequent versioned-docs/chart changes have scoped local QA and a pending minor Changeset.
**Date:** 2026-10-02. The package is `@plain/ui` and its manifest is already `0.2.0`;
no registry publication, remote CI pass, physical-device check, or accessibility
certification is claimed.

## Consumer Changes

The implemented foundation extends neutral defaults with color, legacy accent,
scheme, mode, radius, density, borders, motion, and contrast; semantic and component
tokens; scoped light/dark themes; SSR token/CSS generation; and component extension.
The source-backed API guidance lives in the
[theming reference](../../.agents/skills/p-ui-design/references/theming.md).
Current exports and declarations remain the authority.

The 2026-10-02 refinement keeps neutral defaults intact, softens only opt-in
seeded surface hierarchy, and supplies coordinated categorical chart colors.
Composed series infer colors without configuration. Area gradients and compact
tooltip indicators are defaults; consumer colors, fills and native Recharts
configuration remain overridable. The earlier tone-only refinement received
compilation/build checks without another browser/unit run, as requested at that
stage. The later documentation task has the scoped verification below.

## Migration from 0.1

imports, including CSS and supported subpaths. Check the final package exports
before replacing a subpath; no compatibility alias or automatic npm migration
is promised. Preserve the old name in historical notes.

Before:

```tsx

```

After the rename; verify the exports in the packed candidate:

```tsx

```

### Themes and Brand Components

`theme.color` accepts null or a `#RGB`/`#RRGGBB` hex color. Explicit color takes
precedence; legacy `theme.accent` presets remain the fallback when color is null.
For neutral appearance, reset both `color: null` and `accent: 'neutral'`.
These defaults use the exact hand-authored 0.1 light/dark colors, not generated
Material surfaces. Grayscale palette metadata does not alter those role colors.
Schemes and generated contrast adjustments apply only to a selected color.
`scheme` is `tonal`, `vibrant`, or `expressive`; contrast defaults to zero and is
clamped to `0..1`.

Root token keys remain flat, while component aliases such as
`sidebar.background` map to `--ui-sidebar-background`. `createTheme` returns
`{ color, light, dark, css }`; shared tokens apply to both modes and per-mode
overrides take precedence. Use `@plain/ui/color-theme` for the server helper and
emit its CSS with matching initial theme/direction before paint.

Neutral palette tones are defined in the base CSS and included by
`createTheme({ color: null })`. The shared `control-border` role feeds
`input.border`. The legacy `input-border` key and `input.border` both map to
`--ui-input-border`; do not point that variable at itself. Prefer `control-border`
for shared control boundaries and the component alias for an input-only override.
Default layer tokens are dropdown 100, overlay 80, dialog 90, and toast 110;
explicit native style/engine overrides can change them.

`ThemeScope` accepts light/dark `mode`, tokens, direction, and `componentStyles`.
`extendComponent` and its alias `extend` preserve native props/refs and support
defaults, custom variants, tokens, and typed slot styles. Validate persisted
preferences, portal inheritance, caller overrides, custom palettes, and unstyled
implementations against the integrated candidate.

### Typography

Semantic components are available from `@plain/ui` or `@plain/ui/typography`:
H1-H6, P, Span, Small, Strong, Em, A, Code, Pre, Blockquote, Ul, Ol, Li, and Mark.
Each renders its named HTML tag and preserves element-specific native attributes,
events and refs. Visual size does not change heading level. Use the shared
`typography.root` style slot or native classes/styles to customize them.

```tsx
import { H1, P, A } from '@plain/ui/typography';

export function PageHeading() {
  return (
    <header>
      <H1 size="2xl">Projects</H1>
      <P tone="muted">
        Your workspace. <A href="/projects/new">New project</A>
      </P>
    </header>
  );
}
```

### Copy/Paste Blocks and Templates

Open `/blocks` or `/templates`, choose an example, then copy or download its
complete `.tsx` file. It contains the actual implementation, local state,
sample data, helpers and editable CSS, importing only public UI primitives and
the engines it uses. Keep the file in the consuming application and modify it
like any other React component. There is no `@plain/ui/blocks` or `blocks.css`
entry and no package-level `Block`/`Template` component or registry. The source
generator and private preview registry belong exclusively to the documentation.

Source is fetched on demand rather than including 180 modules in the initial
documentation bundle. Clipboard and download use the same complete module.
The source viewer follows the [APG dialog focus guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
by initially focusing its static heading and restoring the invoking control.

### Sheet/Drawer and Vaul

0.1 uses a Radix Dialog root and `SheetContent side`; Drawer is a bottom dialog
without swipe behavior. The integrated 0.2 Sheet/Drawer implementation uses Vaul.
Set the preferred placement with **root `side`** so placement and gestures agree:

1. Root `side` takes precedence.
2. Native root `direction` is the physical-edge fallback.
3. Legacy `SheetContent side` remains a compatibility fallback.
4. Otherwise Sheet defaults to `end` and Drawer to `bottom`.

Root `side` supports `start`, `end`, `left`, `right`, `top`, and `bottom`. Logical
`start` maps to left in LTR/right in RTL; `end` maps to right in LTR/left in RTL.
The wrapper resolves these through direction context before passing the physical
edge to Vaul. Native `direction` accepts physical edges, not `start`/`end`.

Preferred 0.2 composition:

```tsx
import { Button, Sheet, SheetContent, SheetDescription, SheetTitle, SheetTrigger } from '@plain/ui';

export function ProjectFilters() {
  return (
    <Sheet side="end" dir="rtl">
      <SheetTrigger asChild>
        <Button type="button" variant="outline">
          Filters
        </Button>
      </SheetTrigger>
      <SheetContent>
        <SheetTitle>Project filters</SheetTitle>
        <SheetDescription>Limit the projects in the list.</SheetDescription>
      </SheetContent>
    </Sheet>
  );
}
```

This opens on the left in RTL. Move a legacy content-level placement to the root
when migrating, but do not assume content compatibility was removed. Verify snap
points, dismissal, controlled state, scoped portals, focus restoration, scrolling,
and input behavior in the consuming application; implemented engine support is
not a claim of final browser or physical-device validation.

## Dependency Compatibility

The Material color engine intentionally uses `@material/material-color-utilities`
`^0.3.0`. Local Node 24 ESM import checks found that 0.4 fails because upstream
relative imports omit extensions; the packed consumer passes with 0.3.0. Keep
this compatibility constraint until an upgrade passes Node/SSR import
checks as well as browser builds.

Current Tailwind tooling is **4.3.3**; consumers still do not need Tailwind for
compiled default CSS. Changesets **3.0.3** is installed, with `changeset`,
`release:status`, and `version:packages` npm scripts. Dependency choices follow
the tested package/lockfile and compatibility constraints.

The manifest is already 0.2.0. An empty Changeset acknowledges integration without
another version bump. A new minor Changeset would advance it to 0.3.0; use one
for subsequent consumer changes rather than re-versioning this candidate.
